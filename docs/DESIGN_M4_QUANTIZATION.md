# M4 設計書: リズム量子化・小節割り

作成: 2026-07-18（設計検討のみ、実装未着手）。
前提資料: `docs/DESIGN.md`（v2 設計・開発ルール）、`docs/RESEARCH_2026-07-17.md` §1（v1 失敗分析）、
`docs/STATUS_2026-07-18.md`、`docs/BENCHMARKS.md`。

## 0. 目的とスコープ

notes.json（物理時刻の音符列）から**テンポ・拍・小節構造を推定し、音符を楽譜上の
格子位置（tick）に割り当てる**独立ステージを設計する。成果は MusicXML 出力の
「固定 120BPM・4/4・16分グリッド近似」（`render_musicxml.py` の表示用近似）の置き換え。

v1 の教訓（DESIGN.md 失敗 #4）: ドラムビート推定に依存した量子化が不正確で、
コード内 `# DISABLED` 化で終わった。原因は (a) ドラムステムへの強依存、
(b) 未検証ヒューリスティックの積み上げ、(c) 量子化の正誤を測る評価が存在しなかったこと。
**M4 は評価ファースト**: 量子化メトリクスと専用ベンチを先に作り、方式選定・改善は
すべて実測差分で行う。

スコープ外: 音符検出そのものの改善、奏法記号、スウィング表記の忠実な譜面化
（スウィングは格子割当の課題としては扱う）。

## 1. 前提となる実測ファクト（2026-07-18 調査）

設計判断の根拠として、手元データで以下を実測した（測定スクリプトは scratchpad の
使い捨てプローブ。M4a でベンチハーネスに正式再実装して再現すること）。

### 1.1 GuitarSet の JAMS アノテーション実態（dev 10 + holdout 8 の全 18 トラック確認）

- namespace は `tempo` / `beat_position` / `note_midi` / `chord` / `key_mode` / `pitch_contour`。
- **`tempo`: 全曲グローバル 1 値**（confidence 1.0）。範囲 68〜200 BPM（例: 00_BN3=119.0）。
- **`beat_position`: 拍ごとの時刻 + `measure` / `position` / `num_beats` / `beat_units`**。
  全 18 曲で 4/4、beat 1 が t=0.0、**拍間隔は完全に等間隔**（annotated tempo と誤差 <1e-9）。
  つまり GuitarSet の拍 GT はメトロノーム（クリック）由来の理想格子であり、
  テンポ・拍・小節番号の GT として**厳密に使える**。
- **各音符の楽譜上の位置（何拍目の何分音符か）のアノテーションは存在しない**。

### 1.2 実演奏オンセットは格子からかなり逸脱する（per-note 量子化 GT が作れない）

18 トラックの note_midi onset（計 1,440 ノート）と GT テンポの 16 分格子の距離を実測:

| 指標 | 値 |
|---|---|
| \|逸脱\| の中央値 | 16 分セルの **17.6%**（約 18〜48ms、テンポ依存） |
| 16 分セルの 1/4 以内（= 最近傍スナップが一意に信頼できる帯） | **65.9%** |
| 16 分 + 3 連格子でセル 1/4 以内 | **75.8%**（Jazz 系はスウィングで 3 連解釈が効く） |

含意: **実演奏データでは「最近傍格子 = 正解」とみなせない音符が 24〜34% ある**。
GuitarSet に per-note の楽譜位置 GT がない以上、「量子化の per-note 正解率」は
実データでは定義不能。→ 正解格子位置が構成上既知の**合成ベンチが必須**（§4.3）。

### 1.3 既存ツールのテンポ推定を 18 トラックで素振り実測

ギター単体音源（mic 録音、ミックスなし）に対する素の（無調整）実測:

| 方式 | exact（±4%・オクターブ正しい） | octave-family（×{1/3,1/2,1,2,3} の ±4%） |
|---|---:|---:|
| librosa.beat.beat_track（音声） | 10/18 | 14/18 |
| librosa.feature.rhythm.tempo（onset envelope） | 9/18 | 12/18 |
| 自前 IOI 格子投票（**GT オンセット**入力 = 完璧な転写を仮定した上限） | 7/18 | 13/18 |

観察:

- **支配的な誤りはオクターブ族（半分/2倍/3倍）の取り違え**。完全な MISS は
  librosa で 4/18。テンポの「周期」自体は大半のトラックで取れている。
- IOI 法は完璧なオンセットを与えても exact 7/18 —— 8 分音符主体の曲は
  半分テンポの 16 分と区別が付かず、**オクターブ曖昧性はオンセット列に内在する**。
  IOI 単独方式は主軸にならない（補助・クロスチェック用）。
- 結論: 無調整の既製品ワンショットではゲートに届かない。方式間で誤り方が
  異なる（librosa と IOI の exact 集合は不一致）ため、複数手がかりの統合と
  オクターブ判別の設計が M4a の主作業になる。

### 2.2 推定ソース: ギターステム単体 vs 原曲ミックス

| 論点 | ギターステム（= 転写対象音声） | 原曲ミックス |
|---|---|---|
| v1 の失敗との関係 | ドラム非依存。v1 の轍を構造的に回避 | v1 は「ドラムステムのオンセットに直接スナップ」して失敗。ミックスを**学習済みビートトラッカーの入力**に使うのは依存の質が異なる（トラッカーはミックスで学習されている） |
| ベンチ可能性 | **GuitarSet で今すぐ実測可能**（ギター単体しか存在しない） | GuitarSet にミックスが存在せず、凍結 GT にも拍 GT がない → 実曲での定量ベンチには人手拍ラベルが要る |
| リズム情報量 | 演奏の揺れがそのまま乗る。休符区間で手がかり消失 | ドラム・ベースの拍情報が使える。ただし転写対象と別トラックの頭出しズレはない（同一 source.wav 由来） |

**方針: M4a はギターステム（= 転写に使った音声そのもの）+ 転写ノート onset で開発する。**
理由: (1) GT があるのは GuitarSet だけで、それがギター単体。(2) ドラム非依存の構造的担保。
ミックス入力は M4b で実曲スモークテスト（§5）にて**ステム入力と比較実測**し、
実曲でだけ有効なら「ミックス優先・ステムフォールバック」に切り替える。
どちらを既定にするかは実測で決め、本書では決めない。

### 2.3 採用案

- **M4a で候補 A（librosa + ノート onset 統合）と候補 B（Beat This!）を同一ベンチ・
  同一メトリクスで比較し、実測で採用を決める**（M0 のエンジン選定と同じ流儀）。
- 共通の後段として「オクターブ判別」を独立コンポーネントにする:
  音声系トラッカーのテンポ候補 T に対し {T/2, T, 2T}（必要なら 3T/2 系）を
  転写ノート onset の格子適合度（§1.3 の IOI 格子投票スコア）で採点して選ぶ。
  ここは v1 的なヒューリスティックの温床になり得るので、**構成要素ごとに
  ベンチ差分を記録してから採用**する（開発ルール 3 の適用）。

## 3. 量子化アルゴリズム

### 3.1 候補

| 方式 | 内容 | 複雑さ | 位置づけ |
|---|---|---|---|
| A. グローバル一定テンポ + 位相の格子フィット → 最近傍スナップ | (BPM, 位相) の 2 パラメータで格子を貼り、各 onset を最近傍の許容格子点（16 分 + 必要なら 3 連）へ | 最小 | **M4a**。GuitarSet はクリック録音なので一定テンポ仮定が厳密に成立し、拍推定の質だけを分離して測れる |
| B. 拍単位正規化 | 推定拍列で各拍区間を [0,1) に正規化し、拍内位置を {0, 1/4, 1/3, 1/2, 2/3, 3/4} にスナップ。テンポ変動は拍列が吸収 | 小 | **M4b 第一候補**。テンポ変動対応を自前 DP でなく実績あるビートトラッカーに寄せる（v1 の轍回避） |
| C. 局所テンポ許容 DP / HMM | 状態 =（格子位置, 局所テンポ）で最尤経路を解く（Cemgil 系） | 大 | **M4b 予備**。B が変動ベンチで未達のときのみ。自前実装の検証コストが高い |

M4a を A に固定する理由: 評価の切り分け。A なら「量子化誤り = テンポ・位相推定の誤り +
本質的曖昧性」に分解でき、スナップ規則自体にパラメータがほぼない。
v1 の轍（未検証ヒューリスティックの積層）を避けるため、**M4a のスナップ規則には
分岐を作らない**（音価・休符の整形は MusicXML レンダラ側の既存縮退規則を流用）。

### 3.2 格子の定義

- 基本格子: 拍あたり 4 分割（16 分）+ 3 連（拍あたり 3 分割）。§1.2 の実測で
  3 連追加が Jazz 系の逸脱を明確に減らすことを確認済み。
- tick 表現: **quarter = 12 divisions**（16 分 = 3 tick、3 連 8 分 = 4 tick。4 と 3 の LCM）。
  32 分が必要になった時点で 24 に上げる（スキーマに divisions を明記しておく）。
- 同一格子点に落ちた音は和音（現行 `_quantize()` と同じ扱い）。

## 4. 評価方法（最重要）

### 4.1 メトリクス定義（`eval/metrics.py` に追加、すべて mir_eval ベース）

| メトリクス | 定義 | GT ソース |
|---|---|---|
| **TempoAcc1** | 推定グローバルテンポが GT の ±4% 以内（オクターブも正しい） | JAMS `tempo`（厳密、§1.1） |
| **TempoAcc2** | GT × {1/3, 1/2, 1, 2, 3} のいずれかの ±4% 以内（テンポ推定研究の標準 Accuracy2） | 同上 |
| **Beat F-measure** | `mir_eval.beat.f_measure`（±70ms、標準値） | JAMS `beat_position` |
| **Beat CMLt / AMLt** | 連続正解率（メトリカルレベル厳密 / 許容） | 同上 |
| **Downbeat F-measure** | `beat_position` の position==1 の時刻列に対する F-measure（±70ms） | 同上（M4c） |
| **小節番号一致率** | 各 GT 拍に最近傍の推定拍を対応させ、(measure, position) が一致する拍の割合 | 同上（M4c） |
| **GPA**（Grid Position Accuracy） | 量子化後の (onset_tick) が正解スコアの tick と一致するノートの割合 | **合成ベンチのみ**（§4.3。実データでは定義不能 — §1.2） |
| **量子化変位分布** | \|量子化後時刻 − 元 onset\| の中央値 / p90（診断用。小さいほど良いわけではない点に注意 — 参考統計であり最適化目標にしない） | 実データ・合成とも |

数値目標は §5 のゲートにのみ書く。**実測なしの精度見込みは書かない**（開発ルール 2）。

### 4.2 実データ（GuitarSet）で測れるもの・測れないもの

- 測れる: テンポ・拍・ダウンビート・小節番号（JAMS GT が厳密、§1.1）。
- 測れない: per-note の格子割当の正誤（§1.2 の 24〜34% 曖昧性のため）。
  実データでは GPA を**報告しない**。代わりに「推定格子 vs GT 格子の一致度
  （テンポ・位相）」までを正式メトリクスとする。
- 注意: GuitarSet は全曲 4/4・一定テンポ・beat1=t0 なので、拍子推定・テンポ変動・
  アウフタクト（弱起）の評価には**使えない**。これらは合成ベンチと実曲で補う。

### 4.3 合成リズムベンチ `eval_data/rhythm_synth/`（新規、M4a で構築）

distorted_synth と同じ流儀（生成スクリプト + manifest 同梱、ソースは読み取りのみ）:

1. **参照スコアの生成**: GuitarSet dev の note_midi を GT テンポ格子（16 分 + 3 連）へ
   機械的にスナップし、その結果を**「真のスコア」と定義**する（スナップの当否は
   問題にならない — 音源をこのスコアから再合成するため、構成上 per-note GT が厳密になる）。
2. **音源レンダリング**: 真のスコアを既知テンポ・既知拍子で MIDI 化し、
   ギター音色で合成（第一候補 fluidsynth + サウンドフォント。導入が重い場合は
   Karplus-Strong 自前合成。いずれも manifest にレンダラとパラメータを記録）。
3. **変種**:
   - 一定テンポ（M4a）: GT テンポそのまま + テンポを {0.8×, 1.25×} した変種
   - ヒューマナイズ（M4a）: onset に σ=10ms / 20ms のガウスジッタ
   - テンポ変動（M4b）: 線形リタルダンド（終端 −6%）、中間での急変（+8%）、
     緩慢な揺らぎ（±3% 正弦）
   - 拍子（M4c）: 3/4、6/8 に再構成した変種
4. **採点**: 転写を通さず「真のスコアの物理 onset 列」を直接量子化ステージに入れる
   モード（量子化の単独評価）と、フル転写を通すモード（E2E）を分離して両方測る。
   前者が本命（音符検出の誤差と量子化の誤差を混ぜない）。

限界の明記: 合成音源はレンダラの音色に過適合し得る。よって合成ベンチ(GPA)と
実データベンチ(Tempo/Beat)を**常に両輪で報告**し、片方だけの改善は採用しない。

### 4.4 ベンチハーネスへの統合

- `benchmark.py` に `--rhythm` 系の評価モードを追加し、既存の note-level 表と同形式で
  トラック別 + mean を出力、実測は `docs/BENCHMARKS.md` に追記（既存ルール踏襲）。
- §1.3 のプローブ（librosa / IOI 素振り）はハーネス上で正式に再実測して
  ベースライン行として記録する（scratchpad 測定は参考値扱い）。

## 5. ステージ設計

### 5.1 パイプライン配置

```
transcribe → notes.json ─┬→ tab（運指割当）→ tab.json ──┐
                         └→ quantize → rhythm.json ──────┴→ render_musicxml / render_midi
```

- 新ステージ `quantize`: 入力 = notes.json + （任意）音声ファイル（ステム or ミックス）。
  出力 = `work/{id}/rhythm.json`。tab とは**独立**（運指はリズムに依存しない。
  fingering.py の既知の限界「遷移コストが時間差を無視」の改善は M4 と切り離す）。
- CLI: `guitartab quantize` を単体サブコマンドとして追加（キャッシュ・force は他ステージと同じ規約）。
- **notes.json / tab.json は不変**（現行の非破壊原則を維持）。rhythm.json は追加の
  中間成果物であり、量子化の失敗が転写・運指の成果物を汚染しない。

### 5.2 rhythm.json スキーマ（案）

```jsonc
{
  "schema_version": 1,
  "estimator": "librosa_beat_track",        // 方式と主要パラメータ
  "estimator_params": {"...": "..."},
  "audio_source": "stems/guitar.wav",        // 拍推定に使った音声（null = ノートのみ）
  "tempo_bpm": 119.0,                        // グローバル代表値
  "tempo_map": [                             // 可変テンポ対応（M4a は 1 要素）
    {"time_sec": 0.0, "bpm": 119.0}
  ],
  "time_signature": {"beats": 4, "beat_unit": 4},   // M4b までは 4/4 固定
  "anacrusis_ticks": 0,                      // 弱起（先頭の不完全小節）の長さ
  "divisions_per_quarter": 12,               // 16分=3, 3連8分=4 を表現できる最小値
  "beats": [                                 // 推定拍列（評価・デバッグ用）
    {"time_sec": 0.0, "measure": 1, "position": 1}
  ],
  "notes": [                                 // notes.json と同数・同順（インデックス対応）
    {"onset_tick": 0, "duration_ticks": 6, "deviation_sec": -0.012}
  ]
}
```

- `notes[]` は notes.json とインデックス対応で持つ（評価・デバッグの一次データ）。
- レンダラ向けには時刻→tick の写像（tempo_map + anacrusis）も self-contained に
  なっているため、tab.json 側の音符数が fingering の除外で減っていても
  onset_sec から引ける（tab.json と notes.json の個数不一致に対して頑健）。

### 5.3 レンダラ接続

- `save_musicxml(tab, path, rhythm=None)` に拡張。`rhythm.json` があれば
  そのテンポ・拍子・tick 割当を使い、**なければ現行の固定 120BPM 近似に
  フォールバック**（後方互換。近似モードであることは現行どおり docstring 明記）。
- 現行 `_quantize()`（16 分固定・120BPM）は rhythm 非依存フォールバックとして残し、
  rhythm 供給時は rhythm.json の tick をそのまま使う（レンダラ内で再量子化しない）。
- MIDI レンダラにも tempo map を反映（耳検証で拍が合っているか確認できるようになる
  — 量子化の人手検証手段としても重要）。
- STATUS の残課題 4（五線+TAB 2 段・タイ対応）はこのレンダラ改修と同時に行うのが
  効率的だが、**ゲート評価には含めない**（表示品質と量子化精度を混ぜない）。

## 6. マイルストーン分割とゲート基準

各ゲートは「この数値を実測でクリアするまで次へ進まない」の意味であり、達成見込みの
主張ではない。未達なら方式を替えるか、基準の妥当性をユーザーと再協議する。

### M4a: 一定テンポの拍推定 + 最小量子化

- 内容: 方式 A/B の比較実測（§2.3）、オクターブ判別、格子スナップ（§3.1-A）、
  rhythm.json、メトリクス実装、合成ベンチ（一定テンポ + ジッタ変種）構築、
  MusicXML 接続（rhythm 供給時のみ）。
- 開発は dev 10 トラック、ゲート判定は holdout 8 トラック（M1 と同じ規律。
  holdout でのパラメータ調整禁止）。
- **ゲート基準**:
  - GuitarSet holdout: TempoAcc2 = 8/8、TempoAcc1 ≥ 6/8、Beat F-measure mean ≥ 0.80
  - 合成ベンチ（一定テンポ、真のスコア onset 入力）: GPA ≥ 0.95、
    ジッタ σ=20ms 変種で GPA ≥ 0.85
- TempoAcc1 を 8/8 にしないのは §1.3 の実測でオクターブ曖昧性がデータに内在すると
  確認したため（8 分主体の曲の半分テンポ解釈は譜面としても可読）。ただし
  TempoAcc1 未達分は個別にエラー分析を記録する。

### M4b: テンポ変動対応 + 実曲での推定ソース比較

- 内容: 拍単位正規化（§3.1-B）、合成ベンチのテンポ変動変種、実曲スモークテスト
  （ミックス vs ギターステムの拍推定比較。定量には 2〜3 曲へ人手タップの拍ラベルを
  付ける — GT 凍結ルールに従い、人間が作成・確認したラベルのみを eval_data に置く）。
- **ゲート基準**:
  - 合成テンポ変動変種（リタルダンド −6% / 急変 +8% / 揺らぎ ±3%）: GPA ≥ 0.85
  - 一定テンポベンチの M4a 基準を**維持**（回帰禁止）
  - 実曲人手ラベル（≥2 曲）: Beat F-measure ≥ 0.70
- ソース選定（ミックス/ステム/併用）はこの実測で確定し、DESIGN.md に追記する。

### M4c: 小節割り + 拍子推定

- 内容: ダウンビート推定（Beat This! 採用時はその downbeat 出力、librosa 採用時は
  要追加設計）、弱起（anacrusis）処理、拍子推定（まず 4/4 vs 3/4 の判別から）、
  MusicXML の小節をここで置き換え。
- **ゲート基準**:
  - GuitarSet holdout: Downbeat F-measure mean ≥ 0.70、小節番号一致率 mean ≥ 0.80
  - 合成 3/4・6/8 変種: 拍子判別正解 ≥ 4/6 クリップ（構築時に 6 クリップ以上作る）
- 注意: 実データの拍子 GT が 4/4 しかないため、拍子推定の実データ評価は弱い。
  ここの基準は合成ベンチ偏重になることを明記しておく。

## 7. リスク

1. **実データに per-note リズム GT が存在しない**（§1.2 実測で確定）。合成ベンチ（GPA）が
   唯一の per-note 定量評価であり、合成音源への過適合リスクを常に伴う。
   → 対策: 実データの Tempo/Beat 系メトリクスと両輪報告、MIDI 耳検証の運用。
2. **オクターブ（メトリカルレベル）曖昧性は本質的**（完璧なオンセット入力でも
   exact 7/18、§1.3）。exact テンポにこだわると v1 型のヒューリスティック積層に
   逆戻りする誘因になる。→ 対策: TempoAcc1/2 を分離し、ゲートは Acc2 完全 + Acc1 部分。
3. **GuitarSet の均質性**（全曲 4/4・クリック録音・beat1=t0）。テンポ変動・拍子・弱起の
   実データ評価ができず、M4b/M4c のゲートは合成 + 少数の人手ラベル頼み。
   → 対策: 実曲人手拍ラベルを段階的に増やす（人間作成・凍結の規律は GT ルール準拠）。
4. **Beat This! のドメイン外リスク**: フルミックス学習のモデルにギター単体音源は
   ドメイン外で、性能は未知（未実測）。MPS 動作も未確認。→ M4a の比較実測で判定、
   CPU フォールバック前提でランタイムも記録する。
5. **madmom は使えない**（2018 年から未リリース、numpy2 非互換を確認済み）。既存文献の
   「madmom が定番」という知識に引きずられないこと。
6. **表示検証の自動化困難**: MusicXML の最終見た目は MuseScore 目視になる。
   → 対策: tick 列・小節分割はレンダラ手前（rhythm.json）で完結させ、そこまでを
   ユニットテストで固める（ASCII diff 可能な中間表現を評価する現行方針の踏襲）。
7. **転写誤差との相互作用**: F1 0.88 の転写でも FP/FN がオンセット列を汚し、
   ノート由来の手がかり（オクターブ判別・IOI）を劣化させる。→ 対策: 合成ベンチで
   「真の onset 入力」と「転写経由」を分離採点（§4.3-4）し、劣化幅を定量化する。
